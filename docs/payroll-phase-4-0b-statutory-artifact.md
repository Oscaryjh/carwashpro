# Payroll Data Integrity Phase 4.0B

## Boundary

This phase retains the exact bytes of the first official EPF, PERKESO, or PCB
export for a payroll run and provider revision. It does not add salary effective
dating, employee payroll editing, bank/payment flows, or payroll calculation
changes.

## Artifact lifecycle

1. A finalized payroll with valid current statutory profiles can create revision
   1 of an official export.
2. The exact generated bytes are encrypted with AES-256-GCM and stored once.
3. The artifact identity, tenant, run, provider, revision, and export version are
   authenticated as AAD. SHA-256 and byte length are verified after decryption.
4. Later downloads read only the retained artifact index and encrypted bytes.
   They do not load current employee identity, employer profile, or payroll entry
   data to regenerate the file.
5. Database triggers reject artifact UPDATE and DELETE operations.
6. Export creation, submission state, correction revision, and every download
   create fail-closed audit records.

## Legacy records

Existing submission rows are migrated to `LEGACY_UNVERIFIED`. Their historical
bytes were not retained, so the system does not regenerate or represent them as
verified artifacts. A legacy record remains visible for historical truth only.

## Corrections

A verified rejected revision may create exactly one next `DRAFT` revision. The
rejected artifact remains immutable. Downloading the draft correction creates a
new encrypted artifact from the then-current finalized payroll and statutory
profile. Submitted and accepted revisions cannot be rebuilt or superseded by the
normal reopen flow.

## Payroll reopen rule

Once any statutory submission or correction record exists for a payroll run,
direct Payroll Run reopen is denied in both the UI and service. Corrections use
the statutory revision workflow.

## Key configuration

Both variables are required before a new artifact can be created or an existing
artifact can be downloaded:

```text
STATUTORY_ARTIFACT_ACTIVE_KEY_VERSION=v1
STATUTORY_ARTIFACT_ENCRYPTION_KEYS={"v1":"<32-byte-base64-key>"}
```

- Generate keys with a cryptographically secure random generator.
- Store the keyring only in the environment secret manager.
- Never commit a real key or print it in logs.
- Rotation adds a new version and changes the active version.
- Old key versions must remain available while artifacts encrypted with them
  must be downloadable. Removing an old key makes those artifacts intentionally
  fail closed.
- Back up the keyring separately from the database. Encrypted bytes cannot be
  recovered without their key version.

## Immutability boundary

Artifact bytes and metadata are database-trigger protected against update and
delete. Audit writes follow the Phase 4.0A application append-only and
fail-closed boundary. This is not a substitute for restricted database
administrator access, encrypted backups, key custody, and production retention
policy.

## Deployment gate

Before deploying to an environment:

1. Apply the additive migration.
2. Configure and back up a non-shared environment-specific keyring.
3. Verify one first export, repeated byte-identical download, tamper rejection,
   legacy blocking, rejected correction, and reopen blocking.
4. Confirm no key, plaintext artifact, employee identifier, or statutory amount
   appears in logs or audit payloads.
5. Do not copy Testing keys or artifacts into Production.
